# 포트폴리오 모드 상세 가이드

사용자가 "포트폴리오", "정리", "발표"를 언급하면 이 가이드를 따른다.

## 포트폴리오 정리 템플릿

```
## [기술명] — 포트폴리오 관점

### 내가 한 일 (What I Did)
- 구체적으로 어떤 기능을 구현했는지
- 어떤 문제를 해결했는지
- 코드에서 내가 작성한 핵심 부분 (파일 경로 + 줄 번호)

### 정량적 성과 (Numbers)
- 처리량, 속도, 데이터 규모 등 숫자로 표현
- Before → After 비교 (있다면)

### 기술적 챌린지 (Challenge → Solution)
- 겪었던 문제와 해결 과정
- "처음엔 A였는데, B 문제가 생겨서 C로 바꿨다" 식의 진화 이야기

### 한 줄 요약 (Elevator Pitch)
- 면접에서 30초 안에 설명할 수 있는 한 문장
```

## 프로젝트 정량 데이터 참조

포트폴리오 정리 시 실제 프로젝트 숫자를 코드/DB에서 확인하여 포함한다:

| 항목 | 규모 | 데이터 소스 |
|------|------|-----------|
| 벡터 DB 문서 수 | 656,532건 | LanceDB `legal_chunks` |
| BM25 인덱스 규모 | 425K건 | PostgreSQL `search_text` |
| 변호사 데이터 | 17,326건 | PostgreSQL `lawyers` |
| 법률용어 사전 | 72,700건 | PostgreSQL `legal_terms` |
| MeCab 사용자 사전 | 37,366+ 엔트리 | userdic |
| 임베딩 ONNX 최적화 | 8.97x 속도 향상 | 벤치마크 보고서 |
| 리랭커 ONNX 최적화 | 3.52x 속도 향상 | 벤치마크 보고서 |
| 에이전트 수 | 9개 | `multi_agent/agents/` |
| 자치법규 벡터 | ~240만건 | LanceDB `local_ordinance_chunks` |

## 설계 결정 진화 기록

면접에서 "설계가 어떻게 진화했나요?"에 대한 답변 소재:

| 영역 | Before | After | 이유 |
|------|--------|-------|------|
| 라우팅 | if/else 분기 | RulesRouter + Command 패턴 | 에이전트 9개로 확장 시 관리 불가 |
| 검색 | 벡터 검색만 | 벡터 + BM25 하이브리드 + 리랭킹 | 키워드 정확 매칭 부족 |
| 모델 추론 | PyTorch 직접 | ONNX QDQ INT8 양자화 | 추론 속도 8.97x 개선 필요 |
| 그래프 DB | Neo4j | PostgreSQL Recursive CTE | 인프라 단순화 (DB 하나로 통합) |
| 체크포인터 | InMemorySaver | AsyncPostgresSaver | 서버 재시작 시 대화 유실 방지 |
| 토크나이저 | 기본 MeCab | 법률 userdic 37K 보강 | "손해배상청구권" 등 복합명사 처리 |

## 성능/최적화 성과 정리

### 숫자로 말하기

| 최적화 영역 | Before | After | 개선폭 | 관련 파일 |
|------------|--------|-------|--------|----------|
| 임베딩 추론 | 1,500ms (PyTorch) | 167ms (QDQ INT8) | 8.97x | `onnx_session.py` |
| 리랭커 추론 | 3,240ms (PyTorch) | 920ms (QDQ INT8) | 3.52x | `onnx_session.py` |
| BM25 검색 | 없음 | 하이브리드 | 재현율 향상 | `keyword_search.py` |
| 토크나이저 | 기본 MeCab | 법률 userdic 37K | 정확도 향상 | MeCab userdic |

### 병목 분석 스토리

면접에서 "어떻게 병목을 찾았나요?"에 답할 수 있도록:
- ONNX 프로파일링 결과 참조 (`docs/04-report/features/`)
- MatMul(69.9%) + Attention(25.3%) = 95.2% 병목
- QDQ INT8 양자화로 MatMul 연산 최적화
- 민감 레이어 sweep: 24개 레이어 중 16개를 FP32 유지하여 cosine ≥ 0.999 품질 보존

### 스케일 관점

"10배 커지면?" 질문 대비:
- LanceDB: 로컬 → LanceDB Cloud 또는 분산 저장
- PostgreSQL: 읽기 복제본, 파티셔닝
- 에이전트: 싱글 프로세스 → 큐 기반 비동기 처리
- 임베딩: 배치 처리, GPU 서버 분리

## 엘리베이터 피치 예시

프로젝트 전체를 30초에 설명하는 문장:

> "법률 서비스 플랫폼으로, 65만건의 법령/판례를 벡터+BM25 하이브리드 검색하고,
> LangGraph 기반 9개 에이전트가 사용자 의도에 맞는 법률 상담을 제공합니다.
> ONNX 최적화로 임베딩 추론을 9배 빠르게 만들었고,
> 한국어 법률 도메인에 특화된 MeCab 사전(37K)으로 검색 정확도를 높였습니다."
