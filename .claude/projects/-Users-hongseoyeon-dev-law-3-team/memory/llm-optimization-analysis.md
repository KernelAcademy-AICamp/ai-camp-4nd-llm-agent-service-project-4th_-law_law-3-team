# LLM 호출 최적화 분석 결과 (2026-02-20)

## 핵심 발견

### 현재 상태
- 라우팅: 규칙 기반 (RulesRouter) → LLM 없음 ✓
- 쿼리 리라이팅: follow-up 감지는 휴리스틱 기반이나, follow-up 시 LLM 호출 (1회)
- 응답 생성: 항상 LLM 호출 (1회 또는 streaming)
- 히스토리 처리: 전체 히스토리 포함 → 토큰 낭비

### 예상 절감 효과 (우선순위)

| 순위 | 최적화 항목 | 절감율 | 난이도 | 비고 |
|------|-----------|--------|--------|------|
| 1 | 히스토리 최근 2턴만 사용 | 5~15% | 낮음 | 즉시 적용 |
| 2 | 시스템 프롬프트 축소 (172→40 토큰) | 2~5% | 낮음 | 즉시 적용 |
| 3 | 비-follow-up 시 리라이팅 스킵 강화 | 10~20% | 낮음 | 즉시 적용 |
| 4 | Claude 3.5 Haiku 평가 (부분 대체) | 20~30% | 낮음 | 1주 |
| 5 | RAG 결과 캐싱 | 10~15% | 중간 | 반복성 검증 필요 |
| 6 | 쿼리 리라이팅 병렬화 | TTFB -100ms | 중간 | 스트리밍 최적화 |

## 세부 분석 결과

### 라우팅 분석
- RulesRouter: O(1ms) 완전 최적화됨
- LLM 호출 없음, 규칙 기반만 사용
- **추가 개선 불필요**

### 쿼리 리라이팅 분석
- follow-up 감지: 휴리스틱 기반 (정확도 ~85%)
- follow-up 비율: 추정 30~40%
- LLM 호출: follow-up만 1회
- **현재 구현 우수** (불필요한 호출 회피)

### RAG 검색
- 벡터 + 키워드 검색 (LLM 없음)
- Neo4j 그래프 컨텍스트: 이미 비활성화됨
- **추가 최적화 없음**

### 응답 생성 - 토큰 낭비 발견
```
legal_search_agent._build_messages():
- 10턴 히스토리 × 200토큰 = 2,000토큰 (전체의 50%)
- 시스템 프롬프트: 172토큰 (축소 가능)
```

## 권장 구현 순서

### Phase 1: 즉시 적용 (1~2일, 누적 17~40% 절감)
1. `legal_search_agent._build_messages()`: 히스토리 최근 4개만
2. `legal_search_agent._SYSTEM_PROMPT`: 축소 (172→40 토큰)
3. 기존 follow-up 감지 로직 강화

### Phase 2: 1주
1. Claude 3.5 Haiku 평가 (변호사 통계/찾기)
2. 반복 쿼리 분석 및 캐싱 필요성 검증

### Phase 3: 2주+
1. 쿼리 리라이팅 병렬화
2. 로컬 모델 프로토타이핑
