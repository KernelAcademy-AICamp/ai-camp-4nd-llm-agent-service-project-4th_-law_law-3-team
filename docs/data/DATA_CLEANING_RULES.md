## 1. 단기(檀紀) 날짜 → 서기 변환

### 대상

판례 데이터(`precedents_v1.json`)의 `선고일자` 필드에서 날짜가 단기(檀紀)로 기록된 경우.

- 단기는 서기 + 2333년 (예: 단기 4293년 = 서기 1960년)
- 연도가 3000~5000 범위이면 단기로 판단

### 전수 조사 결과 (2026-02-13)

전체 카테고리의 날짜 필드를 전수 스캔한 결과, **판례만 해당**됩니다.

| 카테고리 | 날짜 필드 | 검사 건수 | 단기 건수 | 결과 |
|----------|----------|----------|----------|------|
| **판례** | `선고일자` | 92,055 | **17건 (0.02%)** | **해당** |
| 헌재결정례 | `종국일자` | 31,717 | 0 | 해당 없음 |
| 행정심판례 | `의결일자` | 33,783 | 0 | 해당 없음 |
| 특별행정심판 | `의결일자` | 63,804 | 0 | 해당 없음 |
| 법령해석례 | `해석일자` | 8,505 | 0 | 해당 없음 |
| 위원회 결정문 | `의결일` | 6,702 | 0 | 해당 없음 |
| 부처 해석례 | `해석일자` | 28,464 | 0 | 해당 없음 |
| 조약 | `서명일자` | 6,167 | 0 | 해당 없음 |

### 단기 판례 예시 (17건)

```
사건번호=4293행65,  선고일자=42931228  → 서기 1960-12-28
사건번호=4289행10,  선고일자=42891030  → 서기 1956-10-30
사건번호=4290행164, 선고일자=42910221  → 서기 1958-02-21
사건번호=4286행2,   선고일자=42861002  → 서기 1953-10-02
사건번호=4287행3,   선고일자=42870227  → 서기 1954-02-27
```

> 모두 1950~60년대 초기 행정소송 판례로, 사건번호 자체도 단기 연도를 사용합니다.

### 변환 로직

```python
DANGI_OFFSET = 2333

def normalize_year(year: int) -> int:
    """단기(4xxx) 연도를 서기로 보정."""
    if 3000 <= year <= 5000:
        return year - DANGI_OFFSET
    return year
```

> 출처: `backend/notebooks/eda/03_temporal_relationships.ipynb`의 `normalize_year` 함수

## 2. 임베딩 데이터 비중 불균형

### 문제

전체 데이터를 임베딩할 경우, 핵심 데이터(판례+법령)의 비중이 비핵심 데이터보다 낮아져 검색 품질이 저하될 수 있습니다.

### 현황 (2026-02-13)

**현재 LanceDB** (판례+법령만 임베딩):

| 데이터 | 청크 수 | 비중 |
|--------|---------|------|
| 판례 | 134,846 | 53.1% |
| 법령 | 118,922 | 46.9% |
| **합계** | **253,768** | **100%** |

> 현재는 판례+법령만 임베딩되어 있어 문제 없음.

**전체 데이터 임베딩 시 예상 비중**:

| 카테고리 | 레코드 수 | 요약 임베딩 비중 | 전문 청킹 비중 |
|----------|----------|-----------------|---------------|
| **판례** | 92,055 | **17.2%** | **19.3%** |
| **법령** | 5,548 | **5.8%** | **5.6%** |
| 판례+법령 합계 | 97,603 | **23.0%** | **24.9%** |
| 특별행정심판 | 148,778 | **35.1%** | **44.9%** |
| 위원회 결정문 | 56,802 | 13.4% | 7.5% |
| 부처 해석례 | 28,464 | 6.7% | 3.8% |
| 행정심판례 | 33,783 | 8.0% | 4.5% |
| 헌재결정례 | 31,717 | 7.5% | 8.3% |
| 기타 | - | 6.3% | 6.1% |

> 특별행정심판(조세심판원 단독 134,932건)이 판례 전체(92,055건)보다 많음.
> 요약 임베딩을 해도 판례+법령(23.0%) < 특별행정심판(35.1%).

### 영향

- **검색 결과 희석**: top-K 결과에 비핵심 데이터가 과다 노출
- **도메인 불일치**: 일반 법률 상담에 조세심판 결정문이 반환될 가능성
- **임베딩 공간 오염**: 벡터 공간에서 핵심 데이터의 클러스터링 약화

### 해결 방안

#### 방법 1: 검색 시 카테고리 필터 (권장, 즉시 적용 가능)

LanceDB 메타데이터 필터로 에이전트별 검색 범위를 제한합니다.

```python
# 기본 검색: 판례+법령만
results = table.search(query_vec).where("data_type IN ('precedent', 'statute')").limit(10)

# 에이전트별 검색 범위
AGENT_SEARCH_SCOPE = {
    "legal_search": ["precedent", "statute"],
    "small_claims": ["precedent", "statute", "cgm_expc"],
    "law_study": ["precedent", "statute", "legislation"],
}
```

- 임베딩 비중과 무관하게 검색 결과 제어 가능
- 기존 RAG 파이프라인에 필터 한 줄 추가로 적용

#### 방법 2: 테이블 분리 (전체 임베딩 시 권장)

```
legal_chunks_core          → 판례 + 법령 (기본 검색 대상)
legal_chunks_supplementary → 특별행정심판, 위원회 결정문, 부처 해석례 등
```

- 기본 검색은 `core` 테이블만 사용
- 특정 에이전트(조세 관련 등)만 `supplementary`도 검색
- 벡터 인덱스를 테이블별로 최적화 가능

#### 방법 3: 검색 시 카테고리 가중치 (Reranking 단계)

```python
CATEGORY_BOOST = {
    "precedent": 1.5,
    "statute": 1.5,
    "constitutional": 1.2,
    "administration": 1.0,
    "special_tribunal": 0.7,
}
final_score = similarity_score * CATEGORY_BOOST[data_type]
```

- 방법 1, 2와 보완적으로 사용

#### 방법 4: 다운샘플링 (비권장)

카테고리별 임베딩 건수에 상한을 두는 방식. 검색 누락이 발생할 수 있어 법률 도메인에서는 비권장.

### 권장 전략

| 우선순위 | 방법 | 적용 시점 |
|---------|------|----------|
| 1 | 카테고리 필터 (방법 1) | 전체 데이터 임베딩 즉시 |
| 2 | 테이블 분리 (방법 2) | 전체 데이터 임베딩 시 설계 |
| 3 | 카테고리 가중치 (방법 3) | 검색 품질 튜닝 시 |
