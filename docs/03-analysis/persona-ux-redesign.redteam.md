> **검증 도구**: Gemini CLI (Red Team)
> **일시**: 2026-02-28

## 1. 취약점 (Security Vulnerabilities)

### [High] 대화 이력 기반 데이터 프라이버시 노출 및 PII 유출
- **분석**: Track 1(AI 분석)은 사용자의 최근 대화 이력을 분석합니다. 변호사-의뢰인 간의 민감한 상담 데이터(이름, 사건번호, 개인정보 등)가 외부 LLM API로 전송될 경우 데이터 유출 및 법적 책임(변호사법 제26조 비밀유지 의무) 이슈가 발생할 수 있습니다.
- **대책**: 분석 단계 전 단계에서 PII(개인식별정보) 마스킹 처리를 선행하고, 데이터 처리 방침에 대한 명시적 동의 절차를 추가해야 합니다.

### [Medium] 비정상적 API 호출을 통한 자원 고갈 (DoS)
- **분석**: `/persona/analyze`는 LLM 연산 비용이 높은 엔드포인트입니다. 공격자가 악의적으로 해당 API를 반복 호출할 경우 인프라 비용 폭증 및 서비스 가용성 저하가 발생합니다.
- **대책**: 사용자당 시간별/일별 호출 횟수 제한(Rate Limiting)을 적용하고, '분석 진행 중' 상태에서는 중복 요청을 차단하는 로직이 필요합니다.

### [Medium] IDOR(Insecure Direct Object Reference) 취약점
- **분석**: `draftState` 또는 `AnalysisInsights`를 프론트엔드에서 관리할 때, API 요청 시 사용자 식별자 유효성 검증이 미흡할 경우 타인의 분석 결과나 설정값을 조회/수정할 위험이 있습니다.
- **대책**: 모든 `/persona/*` 엔드포인트에서 JWT 기반 세션 정보와 요청 객체의 소유권을 반드시 대조 검증해야 합니다.

## 2. 아키텍처 개선 제안

### 외부 서비스 의존성 격리 (Circuit Breaker 도입)
- **문제**: LLM API 장애 시 Track 1 전체가 마비되며 사용자 경험이 급격히 저하됩니다.
- **제안**: 외부 AI 서비스 장애 시 즉시 Track 2(직접 설정)로 우회(Fallback)시키고, 사용자에게 "현재 AI 분석이 지연되어 직접 설정을 안내합니다"라는 안내를 제공하는 서킷 브레이커 패턴을 도입해야 합니다.

### 실시간 상태 동기화 (SSE 고려)
- **문제**: 기획서상 15초의 분석 시간을 '프론트엔드 시뮬레이션'으로 처리하고 있습니다. 이는 실제 API 응답 속도와 괴리가 생길 경우 사용자에게 부정확한 정보를 제공하게 됩니다.
- **제안**: 실제 분석 진행 단계를 백엔드에서 SSE로 전송하여 실시간 진행률을 반영하는 것이 기술적으로 더 견고합니다.

### 상태 영속성 관리 (State Persistence)
- **문제**: `draftState`를 메모리(useState)에서만 관리할 경우, 브라우저 새로고침이나 페이지 이탈 시 수정한 설정값이 유실됩니다.
- **제안**: `SessionStorage` 또는 `IndexedDB`를 활용하여 임시 상태를 로컬에 저장하고, 예기치 못한 종료 후 복귀 시 '이어서 작성' 기능을 제공해야 합니다.

## 3. 고급 기능 추가 제안 (Enterprise Level)

### A/B Testing & Persona Analytics
- AI 추천 수용률(Acceptance Rate)을 정량적으로 트래킹하여 추천 알고리즘을 고도화하는 데이터 피드백 루프를 구축.

### 멀티 페르소나 (Multi-Persona) 지원
- 현업 변호사는 전문 분야가 여러 개일 수 있음. 단일 페르소나가 아닌 '사건 유형별 페르소나'를 저장하고 전환할 수 있는 구조로 확장성 확보.

### 법률 트렌드 연동 칩 (Dynamic Keyword Chips)
- 정적인 추천 키워드 대신, 현재 법조계 이슈(특정 판례, 개정 법안)와 연동된 실시간 트렌드 키워드를 제공.

---

## 4. 성능 최적화 제안

### 분석 결과 캐싱 (Result Caching)
- 대화 이력의 Hash값 또는 마지막 대화 시간을 기준으로 변경 사항이 없을 경우, 이전 분석 결과를 즉시 반환하는 캐싱 레이어 도입.

### Incremental Analysis (증분 분석)
- 전체 이력을 매번 다시 읽는 대신, 마지막 분석 시점 이후의 '추가된 대화'만 분석하여 기존 페르소나를 업데이트하는 방식 도입.

---

## 5. 운영 안정성 제안

### 심층 로깅 및 모니터링 (Observability)
- AI Confidence Score 추이 모니터링
- Track Conversion Drop-off 추적
- Error Logging 세분화 (토큰 부족, 타임아웃, 형식 오류 등)

### LLM 비용 관리 (FinOps)
- 사용자별/기능별 토큰 사용량 대시보드화, 예산 초과 시 알림

### 운영 알림 체계
- Track 1 분석 실패율이 1시간 내 5% 초과 시 운영팀 알림
