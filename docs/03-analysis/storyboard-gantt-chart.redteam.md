### 2. 아키텍처 개선 제안

*   **비동기 워커 기반 처리 (Celery/RabbitMQ):** 현재 백엔드에서 `asyncio.gather`를 통한 배치를 제안하고 있으나, STT(Whisper)나 대용량 파일 분석은 CPU/메모리 집약적인 작업입니다. 이를 API 서버에서 직접 처리하면 다른 요청이 차단될 수 있으므로, 별도의 워커 노드에서 처리하고 상태를 Redis/DB에 저장하는 구조로 전환이 필요합니다.
*   **파일 처리 샌드박스화:** `moviepy`, `pdfminer` 등 외부 파싱 라이브러리는 보안 취약점이 잦습니다. 파일 처리 로직을 권한이 제한된 별도의 컨테이너(Sandbox)에서 실행하여 메인 시스템과 격리해야 합니다.
*   **멱등성(Idempotency) 보장:** 네트워크 오류로 동일 증거가 중복 업로드될 경우, 중복된 타임라인 항목이 생성되지 않도록 파일 해시(SHA-256) 기반의 중복 체크 로직이 아키텍처 레벨에서 지원되어야 합니다.

### 3. 고급 기능 추가 제안 (현업/엔터프라이즈 수준)

*   **증거 무결성 검증 (Hash Chaining):** 법률 증거로서의 효력을 위해 업로드 시점의 파일 해시값을 생성하고 수정 이력을 로그로 남겨 '증거 오염'이 없음을 증명하는 기능.
*   **개인정보 비식별화 (PII Redaction):** AI 분석 전 성명, 전화번호, 주소 등 민감 정보를 자동 마스킹 처리하여 LLM 공급업체(OpenAI/Google)로 전송되는 데이터 최소화.
*   **상충 관계 분석 (Conflict Detection):** 서로 다른 증거(예: A의 카톡 vs B의 녹음)에서 동일 시간대에 상반된 내용이 발견될 경우 간트차트상에 경고 마커 표시.
*   **법률 용어 매핑:** 추출된 `topic`을 한국 표준 법률 분류 체계(검찰/법원 분류)와 매핑하여 변호사가 즉시 인용 가능하도록 지원.

### 4. 성능 최적화 제안

*   **Frontend 가상화 (Windowing):** `vis-timeline`에 수백 개의 항목 렌더링 시 브라우저 부하가 발생할 수 있습니다. 화면에 보이는 영역만 렌더링하는 가상화 기법을 적용해야 합니다.
*   **LLM Context Chunking:** 수년치 카카오톡 대화는 LLM 컨텍스트 한도를 초과합니다. 이를 주 단위나 월 단위로 슬라이딩 윈도우(Sliding Window) 방식으로 나누어 분석하고 요약본을 병합하는 전략이 필요합니다.
*   **CDN 및 이미지 최적화:** 증거 스크린샷 렌더링 시 원본 대신 WebP 포맷의 썸네일을 생성하여 초기 로딩 속도 개선.

### 5. 운영 안정성 제안

*   **AI 비용 모니터링:** 파일당/사용자당 소모되는 토큰 비용을 실시간 추적하고 비정상적인 폭증 시 자동 차단하는 서킷 브레이커(Circuit Breaker) 도입.
*   **추출 정확도 피드백 루프:** AI가 생성한 타임라인을 사용자가 수정할 경우, 해당 데이터를 'Ground Truth'로 저장하여 추후 프롬프트 튜닝 및 모델 평가 데이터셋으로 활용.
*   **분산 트레이싱 (OpenTelemetry):** 다중 파일 분석 시 어떤 단계(STT, Vision, Merge 등)에서 병목이나 오류가 발생하는지 추적하기 위한 트레이싱 로그 구축.
*   **데이터 보존 정책 (Retention Policy):** 법률 데이터의 민감성을 고려하여 사건 종결 시 혹은 일정 기간 미접속 시 데이터를 영구 삭제하는 자동화 정책 수립.
