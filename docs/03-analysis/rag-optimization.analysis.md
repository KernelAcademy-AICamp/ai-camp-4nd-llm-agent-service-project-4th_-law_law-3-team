## 1. 현재 파이프라인 병목 요약

### 전체 응답 흐름 및 소요 시간

```
사용자 질문
    |
[1] 대화형 쿼리 리라이팅     1~1,500ms  (follow-up 시 LLM 호출)
    |
[2] 판례 RAG 검색 ─┐
    |               ├ 병렬 가능 (현재 순차)
[3] 법령 RAG 검색 ─┘
    |
    ├─ 쿼리 임베딩 생성      50~100ms   (KURE-v1, CPU)
    ├─ LanceDB 벡터 검색    100~150ms  (brute-force, 253K 청크)
    ├─ PostgreSQL FTS        10~50ms
    ├─ RRF 병합              <5ms
    ├─ 요약문 배치 조회      50~100ms
    ├─ Cross-encoder 리랭킹  500~800ms  ★ 병목 #2
    └─ 원문 배치 조회        50~100ms
    |
[4] 판례 상세 조회            50~100ms
    |
[5] 컨텍스트/소스 포맷        10~20ms
    |
[6] LLM 최종 응답 생성       2,000~5,000ms  ★★ 최대 병목
    |
응답 반환

총 소요: 3,800~8,200ms (웜스타트)
         5,100~10,200ms (콜드스타트)
```

### 20초 원인 분석

사용자 체감 20초는 다음 요인의 복합 결과로 추정:
- **웜스타트 파이프라인**: 3.8~8.2초
- **콜드스타트 오버헤드**: +1.3~2초 (임베딩/리랭커 모델 최초 로드)
- **네트워크/직렬화**: +0.5~1초
- **Follow-up 쿼리 리라이팅**: +1~1.5초 (2회차 이상 질문)
- **LLM API 지연 변동**: 피크 시 +2~5초
- **DB 연결 풀 경합**: pool_size=5로 동시 요청 시 대기

### 병목 TOP 3

| 순위 | 병목 | 소요 시간 | 전체 비율 | 절감 가능성 |
|------|------|----------|----------|-----------|
| 1 | **LLM 최종 응답 생성** | 2,000~5,000ms | 30~60% | 모델 변경 시 50% |
| 2 | **Cross-encoder 리랭킹** | 500~800ms | 6~10% | 경량 모델 시 80% |
| 3 | **LanceDB 벡터 검색** | 100~150ms | 1~2% | IVF 인덱스 시 50% |

## 2. 최적화 방안 종합

### 2.1 단기 최적화 (1~2일, 설정/소규모 코드 변경)

| # | 최적화 | 예상 절감 | 난이도 | 리스크 | 변경 대상 |
|---|--------|----------|--------|--------|----------|
| S1 | **판례/법령 검색 병렬화** (asyncio.gather) | 250~400ms | 낮음 | 낮음 | `legal_search_agent.py` |
| S2 | **리랭킹 pre-filtering** (similarity>0.5만) | 250~400ms | 낮음 | 중간 | `pipeline.py` |
| S3 | **DB 연결 풀 확대** (pool_size=10, max_overflow=20) | 15~20% 안정화 | 낮음 | 낮음 | `database.py` |
| S4 | **LanceDB IVF 인덱스** (LANCEDB_INDEX_TYPE="IVF_FLAT") | 50~100ms | 낮음 | 낮음 | `.env` |
| S5 | **nprobes 조정** (40→20) | 30~50ms | 낮음 | 중간 | `.env` |
| S6 | **LLM 타이밍 로깅 추가** | 0ms (디버깅) | 낮음 | 없음 | `legal_search_agent.py` |

**단기 적용 시 예상 효과**: 3,800~8,200ms → **3,000~7,000ms** (~15% 개선)

| # | 최적화 | 예상 절감 | 난이도 | 리스크 | 변경 대상 |
|---|--------|----------|--------|--------|----------|
| M1 | **Cross-encoder 경량 모델** (bge-reranker-v2-m3-ko → xs-ko) | 300~500ms | 낮음 | 중간 | `rerank.py` |
| M2 | **쿼리 결과 LRU 캐싱** (1,000개, TTL 5분) | 40~60% (히트 시) | 중간 | 낮음 | `pipeline.py` + 신규 `cache.py` |

## 5. 핵심 발견사항

### 잘 구현된 부분
- RAGPipeline 메트릭 수집 (pipeline.py)
- 적응형 텍스트 truncation (rerank.py)
- Follow-up 쿼리 판정 로직 (query_rewrite.py)
- 하이브리드 검색 구조 (Vector + FTS + RRF)
- 모델 싱글톤 캐싱 (@lru_cache)

### 개선 필요 부분
- LLM 응답 타이밍 로깅 없음 → 정확한 병목 측정 불가
- 판례/법령 검색이 순차 실행 → 병렬화로 즉시 개선 가능
- 리랭킹 시 15개 문서 전체 처리 → top-8 pre-filtering으로 50% 가속
- DB 연결 풀 (pool_size=5) → 동시 요청 시 경합
- LanceDB brute-force → IVF 인덱스로 설정만 변경

### 라우팅은 이미 최적
- **RulesRouter가 규칙 기반**으로 동작 (LLM 호출 없음)
- 라우팅 단계에서는 추가 최적화 불필요
