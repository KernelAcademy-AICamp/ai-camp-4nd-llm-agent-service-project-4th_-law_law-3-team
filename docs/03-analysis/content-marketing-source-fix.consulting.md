## 1. 격차 분석 (현재 vs 목표)

| 영역 | 현재 수준 | 업계 상위권 기준(목표) | 핵심 격차 |
|---|---|---|---|
| 소스 신뢰성 | 7개 중 일부만 실질 반영, 실패 원인 불투명 | 소스별 성공/실패/지연/할당량이 실시간 가시화 | `sources_used` 정합성, 실패 원인 구조화 부족 |
| 아키텍처 일관성 | 기획은 `safe_fetch_with_status`(추가형), QA는 `safe_fetch` 시그니처 변경(파괴형) 제안 | 하위호환 유지 + 점진적 마이그레이션 | 설계-테스트 불일치로 회귀 위험 |
| 품질 검증 체계 | 기능 테스트 중심, 품질/비용/정확도 실험 설계 약함 | 품질 KPI(정확도/중복률/신선도/비용) 기반 실험 운영 | "작동" 검증은 있으나 "품질 향상" 검증은 약함 |
| 운영 관측성 | 로그 중심, 서비스 전 구간 추적 제한 | Trace+Metric+Log 통합 관측, 원인 추적 자동화 | 장애 분석 시간(MTTR) 단축 장치 부족 |
| 수익화 설계 | 기능 정상화 중심 | 플랜/쿼터/리포트 상품화까지 연결 | 기술 수정이 매출 실험으로 연결되지 않음 |

**핵심 판단:**
- 현재 문서는 "버그 수정" 관점으로는 우수하나, "상위 SaaS 수준 운영체계"까지는 아직 1단계 부족합니다.
- 특히 기획서와 QA 전략의 인터페이스 정의가 상충합니다(`safe_fetch` 반환형 변경 vs 추가 메서드).

## 2. 기술 고도화 제안

1. `safe_fetch`는 유지하고 `safe_fetch_with_status`를 표준 경로로 채택하세요.
2. 소스 결과를 `SourceFetchResult`로 통일하고, 에러 분류를 표준 코드(`timeout/auth/rate_limit/network/parse/unknown`)로 고정하세요.
3. LangGraph는 내구 실행(durable execution)+HITL 승인 포인트(법률 도메인 중요 단계)까지 확장하세요.
4. OpenTelemetry 기반으로 API 요청 1건당 "소스별 지연/실패/비용"을 trace에 남기세요.
5. 데이터 계보는 OpenLineage 이벤트로 남겨 "어떤 소스 -> 어떤 키워드 -> 어떤 콘텐츠"가 생성됐는지 추적 가능하게 하세요.
6. 성능 목표는 단일값(15초/20초 혼재) 대신 SLO로 재정의하세요: `P50/P95`, 캐시 히트율, 소스별 timeout율.

## 3. UX 개선 제안

1. "소스 상태 배지"를 단순 성공/실패에서 끝내지 말고 사용자 행동 유도형으로 바꾸세요.
2. 실패 소스에는 즉시 조치 CTA를 붙이세요(예: "API 키 확인", "할당량 초과 안내").
3. 결과 품질 신뢰도를 추가하세요: "근거 소스 수", "최신성", "중복 제거율".
4. 키워드 수집 단계와 뉴스 확장 단계를 UI에서 분리해, 왜 결과가 나왔는지 설명 가능하게 하세요.
5. Google의 생성형 AI 콘텐츠 가이드 기준(정확성/가치/투명성)에 맞춰 자동생성 결과에 출처/생성방식 표기를 권장합니다.

## 4. 데이터 품질 개선 제안

1. QA 기준에 "정확도 지표"를 추가하세요: 법률 관련성, 사실 일치율, 중복률, 신선도.
2. 소스별 가중치/신뢰도 스코어를 도입하세요(커뮤니티/뉴스/영상의 신호 품질 차등 반영).
3. 프롬프트/모델/소스조합 A/B 테스트를 운영해 실제 전환지표(클릭률, 체류시간)와 연결하세요.
4. 캐시에는 `sources_used`, `sources_failed` 외에 `quality_snapshot`(중복률, 평균 신선도)를 함께 저장하세요.
5. 회귀 방지를 위해 계약 테스트를 강화하세요: 스키마 추가 시 프론트 타입 자동 검증 파이프라인 필수.

## 5. 비즈니스 전략 제안

1. 상품 구조를 3단계로 분리하세요: `Starter(기본 소스)`, `Pro(7소스+진단리포트)`, `Enterprise(HITL/감사로그/SLA)`.
2. API 쿼터를 비용 모델과 연결하세요: 소스별 호출비용 기반 사용량 과금 또는 크레딧 방식.
3. 법무법인/변호사 대상 "캠페인 성과 리포트(키워드 -> 콘텐츠 -> 리드)"를 유료 기능으로 만드세요.
4. 운영 KPI를 매출 KPI와 연결하세요: 소스 성공률, 콘텐츠 승인률, 리드 전환률.
5. 단기(4주)는 안정화, 중기(8~12주)는 품질 실험, 장기(분기)는 리포팅/과금 자동화로 로드맵을 분리하세요.

## 6. 종합 평가

- **기획 완성도**: **B+** (원인 정의, 우선순위, 범위 관리가 명확)
- **QA 완성도**: **B** (시나리오는 풍부하나 인터페이스 합의와 품질 KPI가 부족)
- **출시 준비도(현재 기준)**: **중간**

**배포 전 필수 보완 3가지:**

1. `safe_fetch` 인터페이스 최종안(비호환 변경 금지) 확정
2. 성능 목표/SLO 단일화(15초 vs 20초 불일치 해소)
3. 기능 정상화 테스트 + 품질/비용 KPI 테스트를 분리 운영
